Spoken overview
Read the transcript

Every crowd model has parameters: desired speeds, repulsion strengths, floor-field weights. Calibration is choosing their values so that the model matches measurements. Validation is checking the calibrated model against different data it has not seen. Verification comes first and is simpler: does the code do what the equations say? A good calibration uses several observables at once, for example the fundamental diagram, the flow through a bottleneck and travel times, because a model can match one and miss the others. Keep part of the data aside for validation, or the model may only have memorised the data. Standard test cases, such as the RiMEA guideline tests from Germany and the NIST verification tests, check that a simulator behaves sensibly in simple situations: walking speed in a corridor, flow through a door, reaction times. Finally, report uncertainty. Run the model with plausible ranges of parameters and with more than one model if you can, and show how much the answer changes. In this module you will calibrate a fundamental diagram by hand and by computer, and validate it on held-out data.

Three different checks

Verification: is the code right? (A lone person walks at v0; people never pass through walls.) Calibration: which parameter values make the model match data? Validation: does the calibrated model predict data it was not fitted to? Mixing them up is a common error; a perfectly calibrated but unvalidated model may simply have memorised its data.

Calibrating a fundamental diagram

Pick an error measure, often the root mean square error:

RMSE = √( (1/n) Σ (vmodel(ρi) − vi)² )

and search for parameters that minimise it. In the lab, 40 'measured' points from a slower crowd give v0 = 1.08 m/s, γ = 1.60 and ρmax = 6.4 per m², with RMSE 0.055 m/s; on 20 held-out points the RMSE is 0.063. Weidmann's default curve gives 0.174: imported parameters can be badly wrong.

Several observables and standard tests

A model fitted only to the fundamental diagram can still get bottleneck flows or travel times wrong (recall the CA in module 2.3). Calibrate on several observables. Then run standard tests: the German RiMEA guideline tests and the NIST verification and validation tests (Ronchi et al. 2013) check simple behaviours that every simulator should get right.

Reporting uncertainty

Results depend on parameters, random seeds and model choice. Report: the parameter ranges tried, results from repeated stochastic runs (mean and spread), and, where possible, results from a second model. State what the model cannot represent (pushing, groups, information) and how that could bias the answer.

Overfitting

With enough parameters, a model can fit any one data set. Always validate on data you did not use for fitting.

Remember

  • Verification checks code; calibration fits parameters; validation tests on unseen data.
  • Calibrate on several observables, not just one.
  • Standard tests (RiMEA, NIST) check basic simulator behaviour.
  • Report parameter, stochastic and model uncertainty.

Words and links

New words

Verification
Checking that a model's code correctly implements its equations.
Calibration
Choosing parameter values so a model matches measured data.
Validation
Testing a calibrated model against independent data.
RMSE
Root mean square error, a measure of average misfit.
Overfitting
Fitting noise in one data set so the model predicts new data poorly.
RiMEA
German guideline with standard test cases for evacuation simulators.
